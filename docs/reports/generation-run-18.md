# GH-380 Generation Run 18: cmd/ts via SDK Mode

We ran generation run 18 to implement the last deferred release: rel99.2 (ts, the timestamp
utility). This run used SDK mode for the first time, replacing the CLI subprocess mode used
in all previous runs. The run produced cmd/ts — a 408-line implementation with a 157-line
differential test suite — after 11 stitch cycles across one initial run and one resume.

## SDK mode observations

This was the first generation run using SDK mode (cobbler.mode=sdk). Key findings:

1. No 32k output token limit failures. Previous CLI runs failed when the stitch agent
   wrote large files in a single response (run 2 blocked on this). The SDK uses the
   --stdio JSONL protocol with the claude binary, which does not have the same single-
   response limit. All 11 stitch tasks completed without token limit errors.

2. Rate limit events produce a warning: `[SDK WARNING] Failed to parse message from CLI:
   unknown message type (type: rate_limit_event)`. The SDK drops rate_limit_event messages
   rather than surfacing them. The run continued correctly after each such warning. This
   is a minor SDK parsing issue worth filing.

3. Measure prompt size remains at 80,212 bytes (80 KB) with measure_source_mode=headers,
   consistent with previous runs at this codebase scale.

4. Cache utilization was strong on stitches. The largest stitch (cycle 2, 9m30s) used
   1,766,113 cache_read tokens and only 78,779 cache_create tokens. Subsequent stitches
   accumulated cache_read counts up to 700K+ as the context grew.

## Measure loop issue

Starting from cycle 3 in the initial run, the measure agent entered a refinement loop,
repeatedly proposing follow-up ts tasks. Each proposed task covered 4 requirements
(below the P9 minimum of 5-8), triggering a validation warning. Despite the warning,
each task was created and stitched. The LOC trajectory shows this pattern: cycles 3, 6,
and most resume cycles show zero or minimal LOC changes, indicating the stitch agent
was performing verification and minor fixes rather than adding substantive code.

The root cause is that prd004-ts has 8 requirements (R1-R8) but the measure agent
decomposed them into tasks of 4 requirements each, and the stitch agent for the first
task (cycle 2) already implemented most of the full spec. Subsequent measure proposals
targeted gaps the agent perceived in the already-complete implementation.

The measure loop was stopped by closing issue #398 manually after `go build` and
`go test ./cmd/ts/...` confirmed the implementation was correct.
